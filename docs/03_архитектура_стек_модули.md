# Документ 3: Архитектура, Стек и Модули Tomatoro (Конкурсная версия)

> **Статус:** Черновик системного аналитика v2. **Цель:** Зафиксировать технологический стек, пакетную базу, модульную архитектуру бэкенда, админ-панель и стратегию масштабирования. Правило: «Никакой отсебятины».

## 1. Стек технологий и библиотеки (Без отсебятины)

### 1.1. Frontend (Веб-кабинет и Лендинг)

- **Фреймворк:** Next.js 14+ (App Router).
- **UI:** Tailwind CSS + shadcn/ui + Framer Motion (анимации).
- **State:** Zustand.
- **Real-time:** socket.io-client.
- **Браузерное расширение (MV3):** Фреймворк **WXT** (wxt.dev) — современный стандарт для разработки расширений на TypeScript с поддержкой React и HMR. Сборка Manifest V3 из коробки.

### 1.2. Backend (Сервер бизнес-логики)

- **Фреймворк:** FastAPI + Uvicorn.
- **ORM:** SQLAlchemy 2.0 + Alembic.
- **Валидация:** Pydantic v2.
- **Real-time:** python-socketio (с асинхронными обработчиками).
- **Очереди задач (Критично для ИИ):** **Celery + Redis**. ИИ-генерация (GigaChat + SaluteSpeech) занимает 3-5 секунд. Если делать это в потоке WSS, сервер заблокируется. Celery берёт задачу на генерацию, а результат стримит клиенту.
- **Планировщик:** Celery Beat (замена APScheduler, единая точка для cron-задач: списание очков, сброс настроений).
- **HTTP-клиент:** httpx.

### 1.3. AI Orchestrator (Фреймворк ИИ-агента)

- **Фреймворк:** **LangChain** (`langchain` + `langchain-community`). Мы не пишем промпты в сырых строках. LangChain даёт `PromptTemplate`, `LLMChain`, и最重要的是 — **Fallback-механизмы** (если GigaChat падает, LangChain автоматически переключается на YandexGPT или возвращает заглушку).
- **Интеграция GigaChat:** Пакет `gigachat` (официальный SDK Сбера) + `langchain-gigachat` (интеграция с LangChain).
- **TTS:** SaluteSpeech (Сбер) (через REST API).

### 1.4. Биллинг и Уведомления

- **Платежи:** `yookassa` (официальный Python SDK).
- **Web Push (Системные уведомления):** **`pywebpush`**. Стандартная библиотека Python для отправки Web Push по протоколу VAPID. Никаких костылей.

### 1.5. Admin Panel (CRM для управления сервисом)

- **Фреймворк:** SQLAdmin.
- **Авторизация и 2FA:** Используется библиотека `pyotp` для генерации и проверки TOTP-кодов. В таблице `Users` вводится поле `role` (`user` / `admin`) и `totp_secret` (для админов). При входе в `/admin` проверяется роль и валидность 2FA.
- **RBAC (Role-Based Access Control):** SQLAdmin позволяет настроить права доступа. Обычный суппорт (если будет нанят) сможет только смотреть пользователей, но не сможет делать возвраты (доступ к модели YooKassa платежей только на чтение). Основатель имеет полные права.

## 3. Детализация модулей

### 3.1. Модуль Auth & Users (Управление доступом)

- **OAuth2:** Используем `authlib` для интеграции СберID, ВКонтакте, Яндекс ID.
- **Сессии:** JWT-токены. Бэкенд проверяет токен при REST и WSS запросах.
- **Привязки:** Один юзер может привязать все 5 способов входа. Используем таблицу `user_identities`.
- **Проверка статуса бана:** При любом REST или WSS запросе бэкенд проверяет флаг `is_banned`. Если `True`, бэкенд разрывает WSS-соединение и блокирует запуск новых сессий, возвращая ошибку 403.

### 3.2. Модуль Session State Machine (Движок сессий)

- **Как работает:** Принимает события от расширения по WSS. При наступлении статуса `DISTRACTED_SOFT` (> 4 мин), модуль не вызывает GigaChat напрямую. Он формирует JSON с контекстом (цель, тариф, эмоция) и кладёт его в очередь **Redis**.
- **Зачем очередь:** Пока Celery Worker генерирует аудио 5 секунд, FastAPI продолжает обслуживать других юзеров по WSS. Когда аудио готово, Worker стримит его обратно через WSS.

### 3.3. AI Orchestrator (На базе LangChain)

- **Промпт-инжиниринг:** Используем `ChatPromptTemplate`. Контекст: Имя юзера, Сорт помидора (уровень), Цель сессии, Текущее настроение (Бодрый/Печальный/Обиженный), Паттерны (если есть).
- **Fallback (Заглушки):** В LangChain настраивается `with_fallbacks`. Если GigaChat таймаутит или падает 5xx ошибкой, цепочка автоматически возвращает заранее заготовленную статичную фразу (например, «Эй, ты отвлёкся! Возвращайся к цели: {goal}»).
- **TTS:** Сгенерированный текст передаётся в SaluteSpeech. Аудио не сохраняется на диске, отдаётся как бинарный поток.

### 3.4. Модуль Геймификации и Памяти

- **Память-лайт (Паттерны):** Раз в сутки Celery Beat запускает таску `aggregate_patterns`. Она делает `SELECT` по таблице сессий за последние 7 дней. Если находит, что юзер 3 раза сорвал сессию между 15:00 и 17:00, создаёт запись в таблице `user_patterns` со статусом `active`. Оркестратор ИИ при следующем вызове подтянет этот паттерн.
- **Штрафы:** Celery Beat в 04:00 МСК проверяет дату последней сессии. Если вчера сессий не было — списывает 20 FP.

### 3.5. Браузерное расширение (на базе WXT)

- **Архитектура:** Background Service Worker (TS) + Popup (React).
- **Мониторинг:** Слушает `chrome.tabs.onActivated`. Сравнивает URL со списком из `chrome.storage.local`.
- **Web Push:** Расширение подписывается на Web Push (VAPID) при установке. Отправляет endpoint на бэкенд. Когда нужно показать пуш, бэкенд через `pywebpush` шлёт payload. Расширение ловит его через `chrome.push` API (или `self.addEventListener('push')` в Service Worker) и показывает нативный `chrome.notifications`.

## 4. Стратегия масштабирования (От 1000 до 10000+ DAU)

Архитектура изначально проектируется под горизонтальное масштабирование (добавление новых серверов).

1. **Stateless FastAPI:** Серверы API не хранят состояние. Мы можем запустить 5 инстансов FastAPI за Nginx/Traefik. Запросы балансируются.
2. **WebSocket Scaling:** Проблема WSS в том, что юзер подключён к одному серверу. Если Оркестратор на другом сервере сгенерировал аудио, он не сможет отправить его юзеру. Решение: **Redis Pub/Sub**. Все сервера FastAPI слушают Redis. Когда Celery Worker заканчивает генерацию, он публикует сообщение в Redis-канал, и тот сервер, к которому подключён юзер, получает аудио и стримит его.
3. **Celery Workers:** ИИ-генерация — самое тяжёлое. Мы можем запустить 10 Celery Worker-ов, которые будут разгребать очередь
4. В диаграмму бэкенда добавить модуль `ADMIN [SQLAdmin]`, который напрямую связан с ORM SQLAlchemy и имеет доступ ко всем таблицам БД (Users, Payments, Sessions), а также отдельную логику 2FA.

# ДОПОЛНЕНИЕ ОТ ГЛАВНОГО АГЕНТА (2026-09-09): синхронизация с макетами и решениями №23–27

## Д3-1. Замена терминов в модуле Session State Machine

Модуль `SESS [Session State Machine]` переименовать в `SPRINT [Sprint/Pomodoro State Machine]`
(№27). Он ведёт три уровня состояний:

- **Спринт:** planned → focused ⇄ paused → distracted_soft/sad/angry → resumed →
  completed/partial/failed (эскалация ИИ — здесь, как и было).
- **Помодоро:** planned → in_progress → completed/partial/failed/skipped.
- **День:** открытие (утренний план) → активен → завершён (итоги; условие бонуса ПК №26).

Диаграмму (раздел 2) не переписывать: блока `SESS` касается только переименование.
События WSS — см. Документ 5, Д5-2 (`client:sprint_pause/resume`, countdown для
расширения и др.).

## Д3-2. Модуль Геймификации — расширение обязанностей (№26)

К функциям раздела 3.4 добавить Celery-задачи:

- `check_ideal_day` — после последнего завершённого спринта дня: проверить «день
  без срывов», начислить ПК (`daily_bonuses`), отправить `server:day_bonus_granted`.
- `apply_level_multiplier` — при начислении ОФ умножать базу на множитель уровня
  (`level_config.fp_multiplier`, эталонные множители требуют утверждения).
- Новые REST-методы геймификации — Документ 5, Д5-1 (`/gamification/encourage`,
  `/gamification/buy-coins`); списания — только атомарные (Документ 7, Д7-3).

## Д3-3. Модуль Billing — расширение

- Токенизация карт ЮKassa (FR-22): карты хранятся токенами (`payment_cards`),
  списание по токену для автопродления подписки; отмена автопродления — флаг
  `users.auto_renew=false`.
- Частичная оплата (ПК + рубли, FR-26): сначала списываются ПК (атомарно), затем
  инициируется платёж ЮKassa на остаток; при неудаче платежа ПК возвращаются
  (компенсирующая транзакция в той же Celery-задаче).

## Д3-4. Экспорт CSV (FR-21)

Реализация в FastAPI: стриминг `StreamingResponse` без записи на диск (приватность —
Документ 7, Д7-1). Rate-limit 1/10 мин через Redis. Celery-задача не требуется в MVP.

## Д3-5. Cron-расписание Celery Beat — сводка

| Задача | Время | Что делает |
|---|---|---|
| reset_moods | 04:00 МСК | обнуление настроений (как было) |
| apply_decay | 04:00 МСК | суточный штраф −20 ОФ за пропущенный вчера день |
| aggregate_patterns | 03:00 МСК | паттерны из distraction_events JOIN sprints |
| clean_old_activity | 04:30 МСК | архив/удаление активности старше 1 года (переименована) |
| expire_subscriptions | каждые 15 мин | перевод в Базовый при истечении `subscription_expire_date` и `auto_renew=false` |

## Д3-6. WXT-расширение — дополнения

- Пауза (FR-20): в paused-статусе Service Worker не считает отвлечения
  (`chrome.tabs.onActivated` игнорируется), о чём в попапе — плашка «Пауза».
- Обратный отсчёт эскалации (FR-25): поле «Осталось X» обновляется событием
  `server:escalation_countdown` по WSS; при обрыве связи — локальный таймер
  на основе порога из настроек (дублирование недоверенное, только визуальное).
